“我在框架中推行的是**‘双重校验机制’**。

### 2. 实现方案：工具类封装 + 动态 SQL

“具体的实现我是这样做的：

- **底层支撑**：我在 `utils` 包里封装了一个 `DBUtil` 类，基于 JDBC 实现了对数据库的增删改查。
    
- **数据流转**：在 YAML 用例文件中，我会预先定义好‘预期 SQL’。比如下单接口，我会配置一条 `SELECT status FROM orders WHERE order_no = '${order_no}'`。

- **结果对比**：脚本执行完接口请求后，会立刻调用 `DBUtil` 执行这条 SQL，拿到的数据库字段值与 YAML 里的预期结果（比如 `status=1`）进行 `Assert.assertEquals` 对比。”
    

### 3. 痛点处理：异步延迟与数据清理

“在实战中，我还解决了两个比较棘手的问题：

### 2. 实现手段：动态提取与存储

“具体的流转逻辑，我是通过 **JSONPath 技术** 配合一个工具类（`ResponseDataStorage`）来实现的：

- **自动绑定**：提取出来的值会自动存入刚才提到的 `ParamsData` 仓库里，并绑定一个易记的 Key（比如 `orderId`）。

### 3. 技术亮点（这是面试官最想听的）：

    - **原因**：因为我的测试方法参数只定义了一个 `testLogin(CaseInfo caseInfo)`，我把所有接口参数（URL、Header、Body）都封装进了 `CaseInfo` 这一个对象里，所以第二维长度固定为 `1`。

### 6. 性能考虑（进阶问题）

- **面试问题**：如果用例有几万条，一次性加载到 `Object[][]` 会有内存压力吗？
    
- **考察点**：对 **Iterator（迭代器）** 的了解。
    
- **答案要点**：
    
    - **现状**：目前的实现是一次性全部加载进内存。
        
    - **改进**：如果数据量极大，可以将返回值改为 `Iterator<Object[]>`，实现“用一条加载一条”的**懒加载**模式，从而大幅节省内存消耗。

在我参与的一个后台管理系统的项目中，我们遇到了一些关于**用户权限管理**的复杂缺陷。具体问题是，在用户角色切换时，系统没有正确更新用户的访问权限，导致角色切换后，某些用户仍然能够访问他们不应有的资源。

**发现过程**：

1. **问题复现**：最初，通过执行用户角色切换的功能测试，我们发现角色切换后，用户的权限没有及时更新。我们检查了数据库，角色信息已更新，但用户仍能访问之前的权限资源。
    
2. **日志分析**：通过分析系统日志，我发现权限数据的更新并没有同步到**Redis缓存**。系统依赖缓存来验证用户权限，而缓存并没有及时更新，导致权限校验失败。
    

**解决过程**：

1. **问题确认**：与开发团队一起，我们确认了问题根源：角色变更时，Redis缓存未能及时清除或更新。
    
2. **修复方案**：为了修复这个问题，我们决定在用户角色或权限变更时，**清除Redis缓存**，确保下次用户访问时，能从数据库中加载最新的权限信息。我们还增强了缓存更新的逻辑，确保缓存与数据库的数据一致性。
    
3. **测试验证**：我设计了一组新的测试用例，覆盖了角色切换、权限更新以及并发场景，确保所有权限变更能够及时反映在用户的访问权限中。
    
4. **性能考虑**：考虑到系统可能会有高并发的权限变更，我们在清除缓存时使用了异步处理，确保不会影响系统的响应时间。
    

**成果**：  
通过这个过程，我们不仅解决了权限更新的问题，还优化了权限校验机制，提升了系统的健壮性。在高并发和角色切换场景下，系统现在能够稳定地处理权限变更，避免了之前出现的权限错误。
