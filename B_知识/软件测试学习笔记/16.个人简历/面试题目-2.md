第一，快速判断故障影响范围，例如是否影响核心业务以及影响用户数量。如果影响较大，可以先通过回滚版本、关闭功能开关或者限流等方式快速止损，保证系统尽快恢复。

第二，收集故障信息，例如环境、操作步骤、请求参数以及报错信息，并尝试在测试环境复现问题。

第三，通过查看应用日志、数据库日志以及接口返回信息定位问题原因，并与开发和运维一起协同排查。

第四，在问题修复后进行复测并验证线上环境是否恢复正常。

最后，对这次故障进行复盘，例如是否需要补充自动化测试或增加监控，从而避免类似问题再次发生。

接口自动化和 UI 自动化主要区别体现在测试层级和效率上。

首先，UI 自动化主要是模拟用户在页面上的操作，例如点击按钮、输入内容以及验证页面显示结果，因此主要用于验证前端页面的交互流程。

而接口自动化是直接调用系统的接口，例如通过 HTTP 请求调用 API，并验证接口返回结果以及数据库数据，因此更偏向于验证系统后台业务逻辑。

相比之下，接口自动化具有执行速度快、稳定性高和维护成本低的特点，因为它不依赖页面元素定位，也不会受到页面样式变化的影响。因此在实际项目中，很多公司会优先建设接口自动化测试。

# 五、面试标准答案（推荐背）

如果需要避免重复扣款，我一般会从以下几个方面设计测试用例。

第一，测试重复提交场景，例如用户连续点击支付按钮，验证系统是否只扣一次款。

第二，测试接口重复请求，例如对同一个订单连续调用两次支付接口，验证系统是否具有幂等性控制。

第三，测试网络异常场景，例如支付成功但客户端超时，用户再次发起支付请求，系统需要根据订单状态判断是否已经支付成功。

第四，如果系统使用消息队列，还需要测试消息重复消费的情况，验证系统是否能够避免重复扣款。

在金融系统中，核心目标是保证资金一致性，即确保一笔订单只会扣款一次。

# 三、面试标准答案（推荐背）

如果线上接口无法访问，我一般会按照以下步骤排查：

第一，使用 curl 或 Postman 调用接口，确认接口是否真的无法访问，并观察返回的错误信息。

第二，登录服务器查看服务进程，例如通过 `ps -ef` 确认服务是否正常运行。

第三，检查服务端口是否监听，例如通过 `netstat -tlnp` 查看端口是否开启。

第四，检查网络连通性，例如通过 `ping` 或 `telnet` 测试服务器和端口是否可以访问。

第五，查看应用日志，例如通过 `tail -f` 查看服务日志，确认是否存在异常报错。

通过以上步骤逐步定位问题原因。

# 四、金融面试标准答案（推荐版本）

如果需要设计测试用例发现重复扣款问题，我一般会从异常场景进行设计。

第一是重复请求场景，例如用户连续点击支付按钮或接口被重复调用，验证系统是否只扣款一次。

第二是并发场景，例如通过性能工具模拟多个请求同时支付，检查系统是否存在并发导致的重复扣款问题。

第三是网络异常场景，例如支付请求已经发送成功但客户端超时，用户再次发起支付请求，验证系统是否有幂等控制避免重复扣款。

第四是系统异常场景，例如扣款成功但订单状态更新失败，检查系统是否存在资金和订单状态不一致的问题。

最后需要验证系统的幂等机制，例如是否通过订单号或交易ID保证同一笔交易只处理一次，从而避免重复扣款。
