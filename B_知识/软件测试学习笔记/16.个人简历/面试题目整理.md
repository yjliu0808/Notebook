   >

   >  **功能测试：** 我擅长分析复杂的需求并梳理数据流，确保测试用例覆盖。

   >  **自动化测试方面：** 我通常使用 Java、TestNG 和 RestAssured 从零搭建自动化测试框架。    
   >
   > **Performance Testing:** I Use JMeter to simulate real load  and identify performance bottlenecks.I also analyze response time, throughput, and system resource usage to help optimize system performance.

   >  我可以独立完成功能测试、自动化测试和性能测试。这就是我的经验，谢谢！

   

2. 你在项目中是如何落地接口自动化测试的？

   > 如果要在团队落地接口自动化测试，我一般会分为五个步骤。
   >
   > 第一步是调研现状。
   > 我会先了解当前项目的产品形态、发布节奏、历史缺陷情况，以及团队的技术栈，比如是否是 Java 技术体系、接口数量和回归成本等。
   >
   > 第二步是自动化方案选型。
   > 根据团队技术栈选择合适的框架，例如我们团队是 Java 技术栈，我会选择 Java + TestNG + RestAssured 来搭建接口自动化框架，并做一个 PoC 验证。
   >
   > 第三步是分阶段落地。
   > 不会一开始就做全量自动化，而是优先把 核心业务链路和冒烟测试用例实现自动化，然后逐步扩展到主干回归测试，最后实现 全量夜跑自动化。
   >
   > 第四步是接入持续集成。
   > 例如接入 Jenkins，在不同阶段执行不同的自动化任务，比如：
   >
   > 每次代码提交执行 冒烟测试
   >
   > 发布前执行 核心回归测试
   >
   > 每天夜间执行 全量自动化回归
   >
   > 第五步是数据化证明价值。
   > 通过自动化平台统计数据，比如 执行时长、用例覆盖率、缺陷发现率、Flaky rate 等指标，来证明自动化测试确实帮助团队 缩短回归时间，提高系统稳定性和发布效率

3. 你们的接口自动化测试框架是如何设计的？整体架构是怎样的？

   > 我的接口自动化框架是基于 **Java + TestNG + RestAssured** 搭建的，并采用 **分层架构设计**，
   >
   > 用例层：
   > 用 YAML 文件管理测试用例，实现数据和代码分离；
   >
   > 数据层：
   >
   > 通过 SnakeYAML 解析为 CaseInfo 对象，结合 TestNG 的 DataProvider 实现数据驱动；
   >
   > 请求层
   >
   > 使用 RestAssured 发送接口请求，通过占位符机制和全局存储处理接口依赖，比如 token 传递；
   >
   > 断言层
   >
   > 通过状态码断言、JSONPath 数据断言、数据库断言、业务逻辑断言，保证接口测试结果的准确性；
   >
   > 工具层
   >
   > 主要封装一些通用能力，例如：数据库连接、日志管理、配置管理
   >
   > 报告层
   >
   > 通过 Allure 生成报告，并接入 Jenkins 实现持续集成。
   >
   > 整体上是数据驱动 + 分层设计 + 动态参数流转的架构。

   

4. Web 自动化测试和接口自动化测试的区别是什么？各自适用于什么场景？

   > Web 自动化测试和接口自动化测试的主要区别在于测试层级不同。接口自动化属于集成测试，主要验证系统的业务逻辑和数据处理；Web 自动化属于 UI 测试，主要验证前端页面展示和用户操作流程。
   >  从执行效率来看，接口自动化执行速度快、稳定性高、维护成本低，适合做大规模回归测试和持续集成；而 Web 自动化执行速度慢、对环境依赖大、维护成本高，一般用于核心业务流程的端到端测试。
   >  在实际项目中，我们一般遵循测试金字塔模型，以接口自动化为主，Web 自动化为辅，接口自动化覆盖大部分业务逻辑回归测试，Web 自动化覆盖核心用户操作流程，从而在保证测试覆盖率的同时，提高测试效率和稳定性。

5. 如果公司目前还是以手工测试为主，你如何推动测试向质量保证（QA体系）转型？

   如果公司目前还是以手工测试为主，我会从流程规范、自动化测试、质量度量和持续集成四个方面推动测试向 QA 体系转型。首先建立测试流程和发布规范，让测试提前介入需求评审和技术评审，实现测试左移；然后推进接口自动化测试，覆盖核心业务回归测试，提高测试效率；接着建立质量度量体系，比如 Bug 率、自动化覆盖率、发布失败率等，通过数据来衡量质量；最后将自动化测试接入 Jenkins，实现持续集成和持续交付，形成完整的质量保障体系。QA 的核心不是只做测试，而是通过体系和流程来预防问题，提高整体交付质量。

## 二、测试用例设计

1. How do you design test cases? 你设计测试用例的思路是什么？

   我在设计测试用例时，一般会从多个方面考虑，确保测试覆盖全面。首先是功能测试，验证正常业务流程；其次是边界值测试和等价类测试，验证临界值和不同数据范围；然后是异常测试，验证错误输入和异常流程；对于核心业务，还需要做业务流程测试和状态流转测试；另外还需要考虑并发测试、性能测试和安全测试；如果涉及到支付或订单系统，还需要重点关注数据一致性和业务状态是否正确。通过这些方面来设计测试用例，可以保证测试覆盖率和系统质量。

2. 如何设计接口测试用例？需要覆盖哪些测试点？

   设计接口测试用例时，我一般会从参数校验、业务逻辑、边界值、异常场景、权限校验、接口幂等性、并发测试、性能测试以及数据一致性等方面进行设计。首先验证接口的正常业务流程，其次验证参数必填项、参数类型和参数边界值，然后验证异常场景，例如参数错误或数据不存在；对于需要登录的接口，还需要验证 token 和权限控制；对于核心业务接口，如支付接口，还需要重点验证接口幂等性、并发请求处理、回调处理以及数据库数据一致性。通过这些测试点可以保证接口的稳定性和业务数据的正确性。

3. 对于支付系统，你如何设计测试用例？

   > 对于支付系统，我一般会先按照支付业务主链路进行拆分，然后从功能、边界值、异常场景、资金一致性、安全和性能几个方面设计测试用例，确保系统在功能正确、资金安全和高并发情况下都能稳定运行。
   >
   > 首先，在功能测试方面，主要验证支付流程是否正常，例如下单后是否可以正常支付，付款账户余额是否正确扣减，收款账户余额是否正确增加，交易流水和订单状态是否正确生成和更新。
   >
   > 其次，在边界值测试方面，主要验证最小支付金额、最大支付金额、单笔交易限额、单日交易限额，以及账户余额刚好等于支付金额等场景，确保在临界情况下系统处理正确。
   >
   > 在异常场景测试方面，需要重点验证余额不足、账户不存在、支付过程中网络中断、支付失败、支付回调失败等情况，确保即使在异常情况下资金也不会出现错误。
   >
   > 对于支付系统来说，最重要的是资金一致性，需要保证扣款金额、入账金额、订单金额和交易流水金额保持一致。如果支付失败，需要保证事务回滚，或者通过补偿机制保证最终一致性，避免出现重复扣款或资金不一致的问题。
   >
   > 在安全测试方面，需要验证支付密码、身份认证、金额是否可以被篡改、是否存在重复提交导致重复扣款，以及是否存在 SQL 注入或越权操作等安全问题。
   >
   > 最后，在性能测试方面，需要验证高并发支付场景下系统的响应时间、TPS、系统稳定性，以及在高并发情况下是否会出现超卖、重复扣款或系统崩溃等问题。
   >
   > 总体来说，支付系统测试的重点不是简单的功能测试，而是保证资金安全、数据一致性以及系统在高并发情况下的稳定性。

4. 如果支付系统中涉及优惠券、库存，你如何设计测试用例？

   > 如果支付系统中涉及优惠券和库存，我一般会从金额计算、库存扣减、并发场景、幂等性和数据一致性几个方面设计测试用例。
   >
   > 首先在优惠券方面，需要验证优惠券是否可以正常使用，例如优惠券是否满足使用条件、优惠金额计算是否正确、多张优惠券叠加规则是否正确、优惠后支付金额是否正确，以及优惠券使用后状态是否正确更新。
   >
   > 其次在库存方面，需要验证支付成功后库存是否正确扣减，支付失败或订单取消后库存是否回滚，以及在高并发场景下是否会出现超卖问题。
   >
   > 另外还需要重点验证接口幂等性，例如同一个订单重复支付时，不能重复扣库存、不能重复使用优惠券、不能重复扣款。
   >
   > 最后需要验证数据一致性，确保订单金额、优惠金额、支付金额、库存数量在订单系统、库存系统和支付系统之间保持一致，避免出现金额或库存数据不一致的问题。
   >
   > 总体来说，这类场景的测试重点是优惠金额计算正确、库存扣减正确、并发情况下不超卖，以及系统数据一致性。

## 六、性能测试

1. 你是如何开展性能测试的？性能测试流程是怎样的？

   > 性能测试一般按照以下流程开展：
   >
   > 1. 明确性能测试目标，例如 TPS、响应时间、并发用户数等指标。
   > 2. 分析业务场景，确定性能测试场景，例如登录、下单、支付等核心业务。
   > 3. 准备测试数据，例如用户数据、订单数据等。
   > 4. 搭建性能测试环境，保证测试环境与生产环境配置尽量一致。
   > 5. 编写性能测试脚本，例如使用 JMeter 编写接口压测脚本。
   > 6. 执行性能测试，同时监控服务器 CPU、内存、IO、数据库、缓存等资源使用情况。
   > 7. 分析性能瓶颈，例如是应用问题、数据库问题还是系统资源问题。
   > 8. 输出性能测试报告，并给出优化建议。
   >
   > 总结：**性能测试的核心是：压测 → 监控 → 定位 → 优化。**

## 七、CI/CD & Jenkins

1. 你们的接口自动化测试是如何接入 Jenkins 的？

   我们是通过 Jenkins 将接口自动化测试接入到 CI/CD 流程中的。首先将自动化测试项目托管在 Git 仓库中，然后在 Jenkins 中配置 Job 或 Pipeline，当开发提交代码后，Jenkins 会自动拉取代码并通过 Maven 执行自动化测试，用例执行完成后生成 Allure 测试报告，并通过邮件或钉钉发送测试结果。如果核心接口测试未通过，则作为质量门禁阻止发布。同时我们也会配置定时任务，例如每天执行全量回归测试，在发布前执行冒烟测试，从而保证系统的稳定性和发布质量。

2. CI/CD 流程一般是怎么运行的？从代码提交到自动化测试执行的流程是怎样的？

   CI/CD 一般的流程是从代码提交开始，到自动构建、自动测试、自动部署，整体流程如下：

   ```
   开发提交代码 → Git仓库
           ↓
   Jenkins 监听代码提交
           ↓
   拉取最新代码
           ↓
   Maven 编译打包
           ↓
   部署测试环境
           ↓
   执行接口自动化测试
           ↓
   执行UI自动化测试（可选）
           ↓
   生成测试报告（Allure）
           ↓
   发送测试报告（邮件/钉钉）
           ↓
   如果测试通过 → 允许发布
   如果测试失败 → 阻止发布
   ```

## 八、线上问题排查 & 故障定位

1. 如果线上页面显示的时间不正确（例如某网站新闻时间显示为 2026-02-28），你会如何定位这个问题？请说一下排查思路。

   > 如果线上页面显示的时间不正确，我会先通过抓包确认时间是在前端生成的还是后端接口返回的，然后再逐层排查问题。
   >
   > 首先我会打开浏览器开发者工具（F12），在 Network 中抓取页面请求的数据，找到新闻列表接口，查看接口返回的时间字段，例如 `publishTime` 或 `createTime`，确认接口返回的时间是否正确。
   >
   > 如果抓包发现**接口返回的时间就是错误的**，说明问题在后端，需要继续排查后端服务时间、数据库时间或时区配置问题，例如服务器时区是否正确、数据库存储的是不是 UTC 时间、是否做了时区转换等。
   >
   > 如果抓包发现**接口返回时间是正确的，但页面显示是错误的**，说明问题在前端，需要检查前端 JavaScript 是否在做时间格式转换时出现问题，比如时间戳转换错误或时区转换错误。
   >
   > 如果接口返回时间是旧的，还需要检查是否读取了缓存数据，例如 Redis 缓存没有更新，或者读取的是从库数据，主从同步存在延迟。
   >
   > 所以整体排查步骤一般是：
   >
   > 1. 抓包查看接口返回时间是否正确
   > 2. 如果接口时间不对 → 排查后端服务时间、数据库时间、时区问题
   > 3. 如果接口时间正确 → 排查前端时间转换问题
   > 4. 如果接口返回旧数据 → 排查缓存或主从延迟问题
   >
   > 通过抓包可以快速判断问题是在前端、后端、数据库还是缓存，从而快速定位问题。
